<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → API bearer header | A signed token and its claims cross into the backend trust boundary. |
| Clerk → local database | External identity data is copied into application-owned state. |
| local database → request authorization | Local capability rows become the authority for protected actions. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Spoofing | Clerk token verifier | mitigate | Official SDK verification of signature/time/issuer plus authorized parties; no decode-only path. |
| T-06-02 | Spoofing | copied bearer token after deletion | mitigate | Owner-selected durable tombstone is checked before provisioning; provider revocation is handled by the lifecycle plan. |
| T-06-03 | Tampering | first-request race | mitigate | Unique Clerk-subject constraint plus conflict-safe repository and real concurrent-request test. |
| T-06-04 | Elevation of Privilege | admin bootstrap | mitigate | Verified-email allowlist applies only in the create branch; later profile refresh never mutates admin. |
| T-06-05 | Tampering | client identity/role fields | mitigate | Current user comes only from the verified guard resolution; DTOs reject client-supplied identity/capability fields. |
| T-06-06 | Information Disclosure | token/profile logging | mitigate | Omit Authorization/cookies and profile values from logs; sanitized authentication errors. |
| T-06-07 | Information Disclosure | unverified email | mitigate | Explicit verified-email boolean claim is required; email presence alone never qualifies for admin. |
</threat_model>
